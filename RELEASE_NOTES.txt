2026-07-13  |  Phase 2 corrections

Applied review fixes to src/phase2_unsupervised/phase2_unsupervised.py and

WHAT WE CHANGED
------------------------------------------------------------------------
1) Recall-first threshold (main change)
   - Before: the alert cutoff used the max-F1 point (THR = thr_f1).
   - After : it now uses the recall-first point (THR = thr_recall, recall >= 0.85).
   - Why   : Phase 3 can only REMOVE false positives from what Phase 2 flags;
             it can never recover an attack Phase 2 missed. So Phase 2 must
             catch nearly everything (high recall) and let Phase 3 clean up the
             extra false alarms. A max-F1 cutoff was missing 56% of attacks,
             capping the whole system's recall.

2) Leaky-column drop actually works now
   - Before: dropped "http_content_type=application/octet-stream;charset=UTF-8"
             by exact match, which did not match the real feature name -> the
             column was never actually removed (silent no-op).
   - After : matches "port_class_dst" exactly and ANY
             "http_content_type=application/octet-stream*" one-hot, and prints
             how many columns were dropped so it is verifiable.

3) Metrics are now saved to a file
   - Before: metrics only printed to the console.
   - After : all methods + per-attack rates + the chosen threshold are written
             to results/phase2_metrics.json (reproducible, ready for the report).

INTERPRETATION
------------------------------------------------------------------------
- GOOD: Phase 2 now catches ~87% of attacks (was 44%). This is what the
  two-stage design needs - Phase 3 receives almost all real attacks.
- EXPECTED COST: precision falls and false alarms rise sharply (FPR ~45%).
  These ~27k false positives are exactly what the Phase 3 supervised model is
  meant to filter out. The headline Phase 3 result will be "% of these false
  positives removed while keeping the real attacks".
- AUC is unchanged (0.846) because it does not depend on the threshold - only
  the operating point moved.


WHY THE OLD (HIGHER-F1) VERSION WAS NOT THE RIGHT CHOICE
------------------------------------------------------------------------
The old max-F1 threshold LOOKED better in isolation (precision 0.30, F1 0.35),
but Phase 2 is NOT the final output - it is stage 1 of a two-stage cascade.

Hard rule of a cascade: stage 2 can only REMOVE false positives; it can never
recover an attack that stage 1 threw away. At recall 0.44 the old threshold
discarded 56% of attacks BEFORE Phase 3 even started, permanently capping the
whole system's recall at ~44%. No Phase 3 model, however good, could catch what
Phase 2 never flagged.

Analogy: Phase 2 = airport metal detector, Phase 3 = manual bag check. You WANT
the detector to beep at anything suspicious (high recall) even if most beeps are
harmless, because the bag check clears the false beeps. A "precise" detector that
only beeps when certain lets real threats walk through.

Important: we do NOT lose the old version's good precision. The final two-stage
system keeps Phase 2's high recall AND regains high precision from Phase 3 - the
end state beats the old standalone Phase 2 on the metrics that matter.

The recall target is now a single tunable constant (RECALL_TARGET, default 0.85)
at the top of phase2_unsupervised.py, so it can be swept later without code
hunting.


REPRODUCIBILITY (RESOLVED)
